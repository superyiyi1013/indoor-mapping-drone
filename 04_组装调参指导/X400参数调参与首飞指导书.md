# X400 参数调参与首飞指导书

> 适用对象：负责 QGroundControl 配置、PX4 参数调整、传感器校准和首飞验证的成员
>
> 适用平台：Pixhawk 6C + PX4 1.16.2 + QGroundControl + MTF-02 + LQ 数传
>
> 文档目标：让不了解 PX4 参数的人也知道每个关键参数在解决什么问题，如何判断是否配置正确
>
> 数值基准：`02_固件与配置/配置/Pixhawk 6C_3.0.params`

---

## 一、先理解“调参”到底在调什么

很多新成员以为调参就是“把别人给的值抄一遍”。  
实际上，PX4 参数主要是在回答 4 个问题：

1. 飞控接了哪些设备
2. 飞控应该信任哪些传感器
3. 飞控在什么条件下允许起飞
4. 飞机在室内应该飞得多快、多猛、出问题时怎么办

所以参数不是为了“凑完整”，而是为了让飞控形成正确认知：

- 这里没有 GPS
- 这里有光流和测距
- 室内空间小，必须限速限倾角
- 遥控丢失和低电量时要走更保守的保护逻辑

---

## 二、室内无 GPS 飞行为什么必须依赖光流和测距

### 2.1 室外和室内的根本区别

室外飞行常依赖：

- GPS 提供位置
- 气压计辅助高度

室内飞行的问题是：

- GPS 弱或者没有
- 空间更小，速度容错更低
- 需要更稳定的近地高度感知

所以本项目采用：

- 光流做水平运动估计
- 测距做主要高度参考

### 2.2 EKF2 是整个室内方案的核心

`EKF2` 是 PX4 的状态估计器。  
你可以把它理解成“飞控的大脑里负责判断当前状态的模块”。

它会综合：

- IMU
- 磁罗盘
- 气压计
- 光流
- 测距

然后判断：

- 飞机现在是否水平
- 飞机有没有移动
- 飞机离地多高
- 有没有可用的位置估计

如果 EKF2 没有正确融合光流和测距，那么飞机最多只能“姿态稳定”，很难实现可靠的室内悬停。

---

## 三、调参前必须先完成的基础工作

### 3.1 为什么要先做基础校准

调参数之前，必须先让飞控拿到可信的基础传感器数据。否则后面的参数再对，飞控看到的数据还是错的。

至少完成：

1. 加速度计校准
2. 陀螺仪校准
3. 罗盘校准
4. 遥控器校准

### 3.2 每种校准分别在解决什么问题

| 校准项 | 解决的问题 | 不做会怎样 |
|---|---|---|
| 加速度计 | 飞控是否知道什么叫“水平” | 飞机会误判姿态，起飞容易跑偏 |
| 陀螺仪 | 飞控是否知道自己有没有旋转 | 姿态控制会不稳定 |
| 罗盘 | 飞控是否知道航向 | 偏航和位置估计可能异常 |
| 遥控器 | 飞控是否正确理解你的摇杆输入 | 模式切换、油门和方向控制会错乱 |

## 四、端口与串口参数

### 4.1 为什么要先确认端口分工

本项目里最容易出问题的不是“参数数值”，而是“设备接在哪个口、飞控是否知道这个口接了什么”。

统一分工：

| 端口 | 设备 | 作用 |
|---|---|---|
| `TELEM1` | LQ 数传 | 飞控和地面站通信 |
| `TELEM2` | MTF-02 | 光流和测距数据输入 |
| `TELEM3/T3` | 机载电脑 | MAVROS/后续避障链路预留 |

### 4.2 数传相关参数

| 参数名 | 当前值 | 作用 | 为什么这样设 |
|---|---:|---|---|
| `MAV_0_CONFIG` | `101` | 把 MAVLink 实例 0 绑定到 `TELEM1` | 告诉飞控：地面站链路走 TELEM1 |
| `SER_TEL1_BAUD` | `115200` | TELEM1 波特率 | 必须和数传模块一致（LQ 模块最高 115200），否则通信乱码或失联 |
| `MAV_2_CONFIG` | `103` | 把 MAVLink 实例 2 绑定到 `TELEM3/T3` | 2.2 已为机载电脑和 MAVROS 预留链路 |
| `SER_TEL3_BAUD` | `921600` | TELEM3/T3 波特率 | 需要和机载电脑 `fcu_url` 保持一致 |

### 4.3 光流相关串口参数

| 参数名 | 当前值 | 作用 | 为什么这样设 |
|---|---:|---|---|
| `MAV_1_CONFIG` | `102` | 把 MAVLink 实例 1 绑定到 `TELEM2` | 告诉飞控：MTF-02 走 TELEM2 |
| `MAV_1_MODE` | `1` | 串口通信模式 | 保证 TELEM2 按机载设备模式工作 |
| `SER_TEL2_BAUD` | `115200` | TELEM2 波特率 | 必须匹配 MTF-02 的输出波特率 |

### 4.4 串口参数为什么这么关键

因为串口不对时，表现往往很迷惑：

- 飞控能连上电脑
- QGC 能显示基础状态
- 但就是看不到光流或数传

这时不是飞控“坏了”，而是飞控根本没有从正确端口读到正确数据。

## 五、室内无 GPS 的核心参数

### 5.1 告诉飞控“这里没有 GPS”

| 参数名 | 当前值 | 作用 | 为什么这样做 |
|---|---:|---|---|
| `SYS_HAS_GPS` | `0` | 声明本机没有 GPS | 避免系统把 GPS 当成必需硬件 |
| `GPS_1_CONFIG` | `0` | 关闭 GPS1 端口 | 本项目不接 GPS，避免无效搜索 |
| `EKF2_GPS_CTRL` | `0` | 关闭 GPS 融合 | 室内不该依赖 GPS 参与定位 |
| `COM_ARM_WO_GPS` | `1` | 允许无 GPS 解锁 | 不然室内通常无法起飞验证 |

为什么这组参数必须一起理解：

- `SYS_HAS_GPS=0` 是告诉系统“硬件层面没有 GPS”
- `GPS_1_CONFIG=0` 是告诉系统“端口也别等 GPS”
- `EKF2_GPS_CTRL=0` 是告诉估计器“别把 GPS 融合进来”
- `COM_ARM_WO_GPS=1` 是告诉安全检查“无 GPS 也允许调试起飞”

如果只改其中一个，系统行为可能仍然不一致。

## 六、光流与测距参数

### 6.1 为什么光流和测距是室内核心

室内没有 GPS 时：

- 光流负责判断“横向有没有在动”
- 测距负责判断“离地有多高”

如果你把这两个传感器看成“室内版 GPS + 高度计”会更容易理解。

### 6.2 关键参数总表

| 参数名 | 当前值 | 作用 | 解决什么问题 |
|---|---:|---|---|
| `SYS_HAS_NUM_DIST` | `1` | 声明有 1 个测距传感器 | 告诉系统：有高度近距传感器可用 |
| `SYS_HAS_NUM_OF` | `1` | 声明有 1 个光流传感器 | 告诉系统：有光流可用 |
| `EKF2_OF_CTRL` | `1` | 启用光流融合 | 没有它就不会用光流估计水平运动 |
| `EKF2_RNG_CTRL` | `2` | 条件性启用测距融合 | 测距有效时用它，不稳时允许回退 |
| `EKF2_HGT_REF` | `2` | 高度参考源为测距 | 室内高度主要看测距，而不是 GPS |
| `EKF2_BARO_CTRL` | `1` | 保留气压计辅助 | 测距超范围时保留兜底能力 |
| `EKF2_MIN_RNG` | `0.02` | 最小有效测距 2 cm | 过滤过近的不可信数据 |
| `EKF2_RNG_NOISE` | `0.1` | 测距噪声模型 | 告诉 EKF2 这类数据有多抖 |
| `EKF2_RNG_SFE` | `0.05` | 测距误差随高度增长 | 反映距离越远通常越不准 |
| `EKF2_OF_QMIN` | `1` | 光流最低质量门限 | 决定多差的光流数据还会被接受 |
| `EKF2_OF_POS_Z` | `0.06` | 光流安装高度偏移 | 告诉飞控传感器不在飞控中心位置 |
| `EKF2_RNG_POS_Z` | `0.06` | 测距安装高度偏移 | MTF-02 一体模块，必须和光流位置一致 |

### 6.3 这些参数要怎么理解

#### `EKF2_HGT_REF=2`

它的意义是：飞控主要把测距模块当作高度参考。  
这样做解决的是“室内没有稳定 GPS 高度，气压计近地漂移又可能较大”的问题。

#### `EKF2_RNG_CTRL=2`

它的意义是：只要测距数据有效，就优先拿来用；如果超范围或质量不好，就允许系统退回辅助高度源。  
这样做解决的是“MTF-02 很适合低空，但量程有限，不能指望它在所有情况下都一直可靠”。

#### `EKF2_OF_CTRL=1`

它的意义是：允许 EKF2 把光流作为水平运动来源。  
这样做解决的是“没有 GPS 时，飞控仍然需要知道自己是否在向前、向后、向左、向右漂”。

#### `EKF2_OF_QMIN=1`

它的意义是：只要光流质量不是完全差到不能用，就先允许进入融合。  
这样做解决的是“部分室内地面纹理一般，如果门槛太高，系统可能一直等不到够好的光流数据”。

但它也带来风险：

- 门槛低，意味着差一点的数据也可能被吃进去
- 所以后续要通过 `OPTICAL_FLOW_RAD.quality` 实测再决定是否提高到 `10`

### 6.4 光流安装偏移为什么要管

当前参数：

- `EKF2_OF_POS_Z = 0.06`
- `EKF2_RNG_POS_Z = 0.06`

意思是 MTF-02 模块中心在飞控下方约 `6 cm`。  
如果实际安装不是这样，就需要修改。

为什么：

- 飞控做状态估计时默认传感器和机体中心的相对位置是已知的
- 如果偏移填错，动作补偿就可能不准确

## 七、安全与限幅参数

### 7.1 室内为什么要限速限倾角

室外飞行常强调性能，室内飞行更强调容错。  
空间小意味着：

- 速度越大，撞墙越快
- 倾角越大，横向加速度越猛
- 高度变化太快，越容易撞顶或砸地

### 7.2 关键安全参数

| 参数名 | 当前值 | 作用 | 为什么适合室内 |
|---|---:|---|---|
| `MPC_XY_VEL_MAX` | `2.0` | 最大水平速度 | 减少突然冲出和撞墙风险 |
| `MPC_Z_VEL_MAX_UP` | `2.0` | 最大上升速度 | 防止快速冲顶 |
| `MPC_Z_VEL_MAX_DN` | `1.5` | 最大下降速度 | 防止砸地过猛 |
| `MPC_TILTMAX_AIR` | `25` | 自动模式最大倾角 | 控制横向加速不要过激 |
| `MPC_MAN_TILT_MAX` | `35` | 手动模式最大倾角 | 人工接管时也保留一定限制 |
| `MPC_TKO_RAMP_T` | `3.0` | 自动起飞推力爬升时间 | 起飞更柔和，避免突然冲高 |
| `MPC_LAND_SPEED` | `0.6` | 自动降落速度 | 室内降落更保守 |

### 7.3 这些参数分别解决什么问题

#### `MPC_XY_VEL_MAX`

解决的是“飞机横向跑得太快，新手来不及反应”的问题。

#### `MPC_Z_VEL_MAX_UP`

解决的是“室内高度本来就低，飞机一冲就顶到天花板”的问题。

#### `MPC_Z_VEL_MAX_DN`

解决的是“下落过快时地效、操作延迟、场地狭小导致着陆风险大”的问题。

#### `MPC_TILTMAX_AIR`

解决的是“自动模式修正过猛，飞机横着窜”的问题。  
因为对于多旋翼来说，倾角越大，水平加速度通常越大。

## 八、失控保护与低电量保护

### 8.1 为什么室内保护逻辑不能照搬室外

室外很多保护动作会选择返航，但室内没有 GPS 时：

- 返航逻辑可能没有可靠位置基准
- 场地也不适合长距离自动机动

所以室内更适合“保守动作”，比如悬停等待或原地降落。

### 8.2 关键保护参数

| 参数名 | 当前值 | 作用 | 为什么这样设 |
|---|---:|---|---|
| `NAV_RCL_ACT` | `1` | 遥控丢失动作 | 室内优先采用更保守的动作，不应依赖返航 |
| `COM_LOW_BAT_ACT` | `2` | 低电量动作 | 电量低时自动降落，比只报警安全 |

注意：

- 枚举参数不要只看数字，必须在 QGC 中看名称
- 尤其是 `NAV_RCL_ACT`，要在当前固件和 QGC 中确认动作名称

### 8.3 为什么还要设置电池容量

当前参数文件里：

- `BAT1_CAPACITY = -1`

这表示电池容量还没按真实值填写。

为什么必须补上：

- 低电量保护不是凭感觉触发，而是要依赖电压、电流和容量估算剩余电量
- 如果容量不填，系统对“还剩多少电”的判断就不够可靠

你要做的事：

1. 找到实际电池容量
2. 把 `BAT1_CAPACITY` 改成真实 mAh 数值

例如：

- 4200 mAh 电池就填 `4200`
- 5200 mAh 电池就填 `5200`

## 九、飞行模式设置思路

### 9.1 为什么不要只盯着模式数字

`COM_FLTMODE1/4/6` 这类参数在不同资料里常出现数字解释混乱的问题。  
对团队来说，更可靠的做法是：

1. 在 QGC 中直接看模式名称
2. 以模式功能是否符合需求为准

### 9.2 室内首飞推荐顺序

推荐三段开关：

1. `Stabilized`
2. `Altitude`
3. `Hold` 或有效本地位置下的 `Position` 类模式

为什么是这个顺序：

- `Stabilized` 最适合起飞和紧急接管
- `Altitude` 先验证高度控制
- 最后才验证位置保持

### 9.3 为什么“能解锁”不等于“能定点”

因为解锁通过，只说明最低安全条件满足了。  
而能定点，还要求：

1. 光流数据正常
2. 测距数据正常
3. EKF2 已建立可用位置估计

如果这三点没有满足，飞机即使能起飞，也不应该贸然切到定点类模式。

## 十、QGroundControl 实际操作流程

### 10.1 连接与改参

1. 拆桨
2. USB 连接飞控和电脑
3. 打开 QGC
4. 进入 `Vehicle Setup → Parameters`
5. 逐项搜索并修改关键参数
6. 保存
7. 涉及串口绑定和波特率时，重启飞控

为什么优先 USB 而不是数传：

- USB 最稳定
- 带宽更高
- 看 MAVLink 消息更完整

### 10.2 传感器消息验证

进入 `Analyze Tools → MAVLink Inspector`，重点看：

| 消息 | 正常现象 | 说明 |
|---|---|---|
| `DISTANCE_SENSOR` | 抬高或放低飞机时距离会变化 | 说明测距链路正常 |
| `OPTICAL_FLOW_RAD` | 平移飞机时相关字段会变化 | 说明光流链路正常 |

为什么要用消息验证，而不是只看参数页：

- 参数页只能说明“你告诉飞控去用它”
- MAVLink 消息才能说明“飞控真的收到了它的数据”

## 十一、首飞步骤与判断逻辑

### 11.1 起飞前检查

- [ ] 电机顺序正确
- [ ] 电机方向正确
- [ ] 螺旋桨方向正确
- [ ] 遥控器校准正常
- [ ] 模式开关正常
- [ ] `DISTANCE_SENSOR` 正常
- [ ] `OPTICAL_FLOW_RAD` 正常
- [ ] 电池容量参数已确认
- [ ] 周围有足够安全空间

### 11.2 首飞推荐步骤

1. `Stabilized` 解锁
2. 轻推油门，低空离地 `20~50 cm`
3. 观察是否明显偏航、侧翻、振动异常
4. 切到 `Altitude`，观察是否能稳定定高
5. 若定高正常，再尝试 `Hold/Position 类` 模式

### 11.3 每一步分别在验证什么

#### `Stabilized`

验证的是：

- 电机顺序对不对
- 飞控姿态方向对不对
- 机体有没有明显机械问题

#### `Altitude`

验证的是：

- 测距和高度控制链路是否基本正常
- 油门控制是否变得更平稳

#### `Hold/Position 类`

验证的是：

- 光流是否参与水平控制
- EKF2 是否建立了足够可靠的位置估计

## 十二、常见问题与排查思路

### 12.1 看不到 `DISTANCE_SENSOR`

优先查：

1. TELEM2 接线是否交叉
2. MTF-02 是否上电
3. `SER_TEL2_BAUD` 是否为 `115200`
4. `MAV_1_CONFIG` 是否正确

### 12.2 看得到测距但看不到光流

说明串口可能是通的，但光流部分没有正常工作。  
优先查：

1. 地面纹理是否足够
2. 光照是否合适
3. 模块方向是否正确
4. 模块输出协议是否正确

### 12.3 定高正常但横向漂

通常说明：

- 测距在工作
- 光流质量不足或融合不稳

排查方向：

1. 观察 `OPTICAL_FLOW_RAD.quality`
2. 更换有纹理地面
3. 检查模块是否松动
4. 对比尝试提高 `EKF2_OF_QMIN`

### 12.4 起飞正常但一切定点就乱跑

这说明“姿态控制基本正常”，但“位置估计或位置控制链路不稳定”。

常见原因：

1. 光流方向不对
2. 光流质量差
3. 测距数据跳变
4. 过早进入定点模式

### 12.5 低电量保护不可靠

优先查：

1. `BAT1_CAPACITY` 是否已填写真实值
2. 电池芯数是否为 `4`
3. PM06 电压电流检测是否正常

## 十四、MAVLink Console 速查

> **入口**：QGC → Analyze Tools → MAVLink Console，出现 `nsh>` 即进入。
> ⚠️ 建议 USB 连接，数传下避免长时间监听高频主题。

### 14.1 参数设置与检查

```sh
# 设参 -> 保存 -> 重启
param set EKF2_IMU_POS_Z -0.04
param set EKF2_OF_POS_Z 0.06
param set EKF2_RNG_POS_Z 0.06
param save                              # 必须保存，否则重启丢失
reboot                                  # 串口/传感器参数需重启

# 查看参数
param show EKF2_OF_POS_Z                # 单个
param show EKF2*                        # 通配符搜索
param show --diffs                      # 只看改过的（最实用）

# 恢复默认
param set EKF2_OF_POS_Z default

# 从 SD 卡批量加载
param load /fs/microsd/params/xxx.params && param save
```

### 14.2 监听命令

```sh
listener <主题> [条数]     # Ctrl+C 持续退出
```

常用监听（建议加条数限制）：

```sh
listener distance_sensor 5              # 测距
listener optical_flow_rad 5             # 光流
listener vehicle_local_position 5       # 位置/速度/高度
listener estimator_status_flags 5       # EKF2 融合状态
listener estimator_innovations 5        # 融合质量
listener battery_status 5               # 电池
listener vehicle_status 5               # 模式/解锁
```

### 14.3 判读

| 主题 | 正常 | 异常 |
|---|---|---|
| `distance_sensor` | 随高度变 | 固定/为0 |
| `optical_flow_rad` | quality>60 | 长期为0 |
| `vehicle_local_position` | valid=True | valid=False |
| `estimator_status_flags` | cs.opt_flow=true | false(光流未融合) |
| `estimator_innovations` | +-0.1 波动 | 持续>0.5 |

### 14.4 排查顺序

```sh
listener distance_sensor 3              # 1. 测距通？
listener optical_flow_rad 3             # 2. 光流通？
listener estimator_status_flags 3       # 3. EKF2 融合了？
listener vehicle_local_position 3       # 4. 位置有效？
```

### 14.5 其他

```sh
top        # CPU/任务栈
free       # 内存
dmesg      # 启动日志
reboot     # 重启
```

### 14.6 要点

- **设参后必须 `param save`**。
- **`param show --diffs`** 快速复核改过的参数。
- **监听加条数限制**，避免阻塞数传。
- **监听输出可粘贴到阶段测试文档**作为记录。

## 十五、结论

参数调试的核心不是"把值填进 QGC"，而是打通下面这条逻辑链：

`飞控知道没有 GPS → 飞控知道光流和测距存在 → 飞控真的收到光流和测距数据 → EKF2 正确融合 → 速度和倾角被限制在室内安全范围 → 低电量和失控保护逻辑可用`

只要这条链路打通，新成员即使不懂全部 PX4 细节，也能完成本项目的室内装机、调参和首飞验证。
