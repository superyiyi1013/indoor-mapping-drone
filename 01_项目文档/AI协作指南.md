# AI 协作指南

> 用途：新开 AI 对话时，按本指南让 AI 快速接手项目，避免重复解释和结论散落。

---

## 1. 新开对话提示词（直接复制）

```text
你现在接手 Pixhawk 6C + X400 项目。请先按以下顺序读取项目文件：

1. CLAUDE.md（项目根目录）                            ← 项目状态、当前目标、关键结论
2. 01_项目文档/问题跟踪索引.md                        ← 已知问题一览（可据此决定是否深入读修复记录）
3. 当前阶段测试文件（路径在 CLAUDE.md 中查找）         ← 当前要做的测试内容

如果需要详细了解某个历史问题的根因和改动，再读：
03_SourceCode/问题修复记录/对应文件.md

当前项目原则：
1. 先排查原因，不要马上修改文件；
2. 只装了前向 D435i，只做前向避障；
3. 每完成一个阶段或修复一个问题，同步更新 CLAUDE.md 和问题跟踪索引.md；
4. 代码修改先判断属于哪一层：Windows MAVLink / Linux MAVROS / Linux ROS 感知 / flight_core 共享层。

请基于这些事实继续协助我做后续开发和测试。
```

## 2. 常用说法模板

### 只排查、不改文件

```text
我们先讨论和排查原因，暂时不要修改任何文件。请基于 CLAUDE.md 和当前阶段测试文档分析。
```

需要连接机载电脑时加这句：

```text
你现在可以连接机载电脑/MAVROS。只做只读排查，不修改文件不改参数。执行 rostopic、rosnode、rosparam、PX4 listener 检查，给证据和结论。
```

### 修改文档或代码

```text
请把这次确认的结论写入 CLAUDE.md 的维护区，并同步更新当前阶段测试文档。不要改无关文件。
```

```text
请先说明要改哪个模块、为什么属于这个模块，再做最小范围修改。修改后列出验证命令和仍需机载电脑实测的部分。
```

### 创建问题修复记录 + 更新跟踪索引

修复完一个问题后，让 AI 同时做两件事：

```text
请根据本次诊断和修改，完成以下工作：
1. 在 03_SourceCode/问题修复记录/ 中创建修复文档，按已有文件的命名风格和格式
2. 在 01_项目文档/问题跟踪索引.md 中追加一行，状态标为 🔵 已修复待验证
3. 同步更新 CLAUDE.md 的维护区

创建前先列出你要写的内容概要给我确认。
```

### 更新问题跟踪索引状态

验证通过/失败后，更新索引状态：

```text
请把 问题跟踪索引.md 中"XX问题"的状态更新为 <✅ 已关闭 / 🟡 复现中>，并在已关闭表格中补充验证结论。
```

### 参数基线同步

```text
参数基线已更新。新文件位于：
02_固件与配置/参数配置/Pixhawk 6C_X.X.params

请扫描项目所有文件（包括代码注释），找出所有引用旧版本号的地方。
先列出所有需要修改的文件和行号给我确认，确认后统一执行替换。
```

## 3. 维护体系

### 核心文件分工

| 文件 | 用途 | 谁维护 | 更新时机 |
|---|---|---|---|
| `CLAUDE.md（项目根目录）` | AI 第一入口：项目状态、当前目标、关键链路结论、禁止踩坑 | 人 + AI | 阶段推进、关键结论确认后 |
| `01_项目文档/问题跟踪索引.md` | 已知问题一览表，每条一行 | AI | 创建/关闭修复记录时 |
| `03_SourceCode/问题修复记录/*.md` | 每个问题的完整根因分析、改动内容和验证要点 | AI | 每次定位并修复问题后 |
| `03_SourceCode/test/00_总控/03_当前参数基线.md` | 参数基线文档，与实际 .params 文件保持一致 | AI | 参数变更后 |

### 更新规则

1. **修复问题**：创建修复记录 → 同步更新问题跟踪索引（加一行）→ 更新 CLAUDE.md（加禁止踩坑规则）
2. **阶段推进**：更新 CLAUDE.md 中的当前目标
3. **参数变更**：更新参数基线文档，同步 .params 文件
4. **旧结论被推翻**：在 CLAUDE.md 中明确写"旧结论废弃"，不要并列堆积

### 问题状态流转

```
🔵 已修复待验证  → 验证通过  → ✅ 已关闭
                 → 验证失败  → 🟡 复现中
🟡 复现中       → 找到方案  → 🔵 已修复待验证
                 → 放弃修复  → ❌ 已放弃
```

### 好的维护标准

- 写确认事实，不写模糊猜测
- 写对后续有用的结论，不写完整聊天流水账
- 参数、日志、topic、文件路径写准确
- 每条尽量能指导下一次 AI 行动

## 4. SSH 现场测试提示词

> 下面的提示词可以直接复制给 Codex/CLI AI，用于 SSH 到机载电脑协助测试。

测试脚本：

测试中请重点记录以下信息，并在最终总结中按这些项目整理：

一、起飞阶段

请记录：
- 地面基准 home_z
- 起跳台阶目标
- 起跳中每次打印的相对高度
- 判定"已离地"时的相对高度
- 0.5m 以下是否有高度停滞、反复、回落或明显等待
- 从起跳到 0.5m 附近是否显得不够果断

二、悬停定位阶段

三、降落阶段

- 进入低空降落段时的高度

- 低空段当前相对高度和下降目标
- 是否出现 30~40cm 附近动力突然增强、小漂移、横向修正
- 触地候选高度
- 触地确认高度
- 上锁尝试次数、service_ok、armed 状态

请特别关注类似日志：

- 低空段是否仍然使用同一个锁定 XY；

四、异常后必须立即抓取的数据

- 悬停明显漂移；
- 降落明显横向漂移；
- 触地后上锁失败；

rostopic echo -n 1 /mavros/local_position/pose

然后根据这些数据判断：
- 当前是否 connected；
- 当前是否 armed；
- 当前模式 mode 是什么；
- landed_state 是多少；
- local_position 的 x/y/z 是否异常；
- 再次 arming false 是否 success；
- 问题更像是起飞问题、定位问题、低空降落控制问题，还是上锁时序问题。

测试结束后，请按下面格式总结，不要泛泛而谈：

3. 降落结论

- 进入低空段高度：
- 低空段是否发生 XY 跳变：
- 是否有 30~40cm 动力增强/漂移：
- 触地候选高度：
- 上锁尝试结果：

4. 异常判断
